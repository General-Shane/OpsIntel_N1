# 1. PURPOSE

This document defines the complete automated reporting lifecycle.

The target automation is:

``` text
DATA AVAILABLE
      ↓
DATA PROCESSED
      ↓
ANALYTICS REFRESHED
      ↓
REPORT PERIOD DETERMINED
      ↓
REPORT GENERATED
      ↓
AI EXECUTIVE NARRATIVE
      ↓
REPORT VALIDATED
      ↓
REPORT STORED
      ↓
NOTIFICATION SENT
      ↓
EXECUTION RECORDED
```

The system must support:

``` text
Daily
Weekly
Monthly
```

reports plus:

``` text
Generate Now
Send Test
```

for demonstration and troubleshooting.

------------------------------------------------------------------------

# 2. AUTOMATION PRINCIPLE

The POC must demonstrate genuine automation.

It should not merely provide a button called:

``` text
Generate Report
```

and claim automation.

A scheduled execution must automatically:

1.  determine the reporting period;
2.  retrieve the correct dataset;
3.  calculate metrics;
4.  generate insights;
5.  compose the report;
6.  generate the report artifact;
7.  save it;
8.  record execution;
9.  notify the configured channel.

# 10. REPORT PERIOD RULE

Report periods must be generated centrally.

Do not let each report template invent date logic.

Use:

``` text
PeriodResolver
```

------------------------------------------------------------------------

# 11. DAILY PERIOD

Default:

``` text
previous calendar day
```

Example:

If generated on:

``` text
09 Aug
```

daily report period:

``` text
08 Aug 00:00
→
08 Aug 23:59:59
```

Timezone comes from configured reporting timezone.

------------------------------------------------------------------------

# 12. WEEKLY PERIOD

Default:

``` text
previous completed calendar week
```

Example:

If Monday is the first day:

``` text
Monday 00:00
→
Sunday 23:59:59
```

Do not generate a "weekly" report using a partially completed current
week unless explicitly configured.

------------------------------------------------------------------------

# 13. MONTHLY PERIOD

Default:

``` text
previous completed calendar month
```

Example:

Report generated on:

``` text
01 September
```

Period:

``` text

```

reporting period.

``` text

```

``` text

```


# 56. NOTIFICATION FAILURE

``` text

```

failed.

------------------------------------------------------------------------

# 57. RETRY POLICY

For transient notification failure:

``` text
max 2–3 retries
```

Use backoff where practical.

Do not retry permanent configuration errors.

------------------------------------------------------------------------

# 58. REPORT RETRY

If report generation fails due to transient infrastructure issues:

-   record failure;
-   allow controlled retry;
-   do not create uncontrolled duplicate reports.

# 72. DAILY EDGE CASE

``` text

```

------------------------------------------------------------------------

# 73. DUPLICATE EXECUTION PREVENTION

Scheduler must prevent duplicate execution caused by:

-   application restart;
-   job re-registration;
-   manual retry;
-   overlapping scheduler runs.

Use an execution key.

------------------------------------------------------------------------

# 74. OVERLAPPING REPORTS

If a report of the same type is already running:

``` text
RUNNING
```

do not start another identical scheduled execution.

------------------------------------------------------------------------

# 75. JOB LOCK

Use a simple lock mechanism suitable for V1.

# 85. REPORT DEFINITION OF DONE

Reporting is complete when:

-   daily report exists;
-   weekly report exists;
-   monthly report exists;
-   HTML generation works;
-   PDF generation works;
-   report history works;
-   manual generation works;
-   AI narrative works/fallback works;
-   validation works;
-   storage works;
-   report download works;
-   execution history works.

------------------------------------------------------------------------

# 86. SCHEDULER DEFINITION OF DONE

Scheduler is complete when:

-   daily schedule works;
-   weekly schedule works;
-   monthly schedule works;
-   enable/disable works;
-   next-run is displayed;
-   run-now works;
-   duplicate prevention works;
-   execution history works;
-   failures are recorded.

------------------------------------------------------------------------

# 87. NOTIFICATION DEFINITION OF DONE

Notifications are complete when:

-   provider abstraction exists;
-   Teams workflow/webhook integration works when configured;
-   Slack webhook works when configured;
-   test send works;
-   failures are recorded;
-   retry works for transient failures;
-   report success is independent of notification failure.

